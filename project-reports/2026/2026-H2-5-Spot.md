# Project Overview

5-Spot is a cloud-native Kubernetes controller, written in Rust, that adds and removes physical machines from Cluster API (CAPI) clusters on a schedule. It lets a firm lend idle hardware (for example, trading or risk hosts outside market hours) to a Kubernetes cluster and hand it back, drained and clean, before the incumbent workload needs it. Typical uses are cost optimisation, energy reduction, and on-demand test or batch capacity on hardware that already exists.

This is the project's first TOC health review. The repository was contributed to FINOS in April 2026, so this report covers April to November 2026.

- **Architecture-driven development**: 21 Architecture Decision Records in [`docs/adr/`](https://github.com/finos/5-spot/tree/main/docs/adr), and a [FINOS CALM](https://calm.finos.org/) model of the system kept in step with the code. - **Supply chain and security posture**: OpenSSF Scorecard **8.3**, OpenSSF Best Practices badge at 99% passing, SLSA Level 3 provenance, Cosign-signed images, signed VEX documents, signed-commit enforcement, cargo-deny / cargo-audit / Trivy / Semgrep / Gitleaks / CodeQL in CI, and a published [threat model](https://github.com/finos/5-spot/blob/main/docs/src/security/threat-model.md). `SECURITY.md` includes a CRA escalation section (contributed by FINOS staff).
- **Test depth**: roughly 980 unit and integration tests, plus two automated end-to-end tiers in `kind`, including a real k0smotron hosted control plane ([ADR 0019](https://github.com/finos/5-spot/blob/main/docs/adr/0019-k0smotron-end-to-end-tier-in-kind.md)).

## Major milestones achieved

- **`v0.2.x`**: Apache 2.0 relicensing and technical charter, CALM architecture model, emergency node reclaim by process match, user-defined node taints, Kata runtime mutating policy, VEX generation and signing.
- **`v0.3.0`**: pluggable spot-schedule provider architecture, with schedules as first-class provider references (including a "capital markets" calendar provider); CRD moved from `v1alpha1` to `v1beta1` with conversion; per-node Kata containerd config delivery; support for multiple CAPI bootstrap and infrastructure contract versions.
- **`v0.3.2`**: new `ScheduledCapacity` CRD and a separately-identified capacity controller, for the "non-handover" pattern where a host stays in the cluster and a bounded slice of it is conceded on a schedule ([ADR 0011](https://github.com/finos/5-spot/blob/main/docs/adr/0011-schedule-gated-capacity-separate-controller.md)).
- **`v0.4.0`**: 5-Spot creates and owns the capacity object ([ADR 0016](https://github.com/finos/5-spot/blob/main/docs/adr/0016-own-the-capacity-object.md)); one binary and one image with subcommands ([ADR 0020](https://github.com/finos/5-spot/blob/main/docs/adr/0020-one-binary-one-image-with-subcommands.md)); reclaim agent no longer needs `NET_ADMIN` ([ADR 0021](https://github.com/finos/5-spot/blob/main/docs/adr/0021-reclaim-agent-polls-proc-no-net-admin.md)).
- **Validated on real infrastructure**: first full activate / deactivate / reactivate cycle against a k0smotron hosted control plane and SSH-provisioned bare-metal workers on CAPI v1.14 (`v1beta2`). This surfaced and fixed defects no unit test could reach, and produced a published guide on [confining a worker with cgroups](https://github.com/finos/5-spot/blob/main/docs/src/guides/confining-a-worker-with-cgroups.md).

## New features delivered

- Time-based scheduling with timezones, day and hour ranges, and pluggable schedule providers
- Graceful shutdown with configurable grace periods and node draining
- Emergency kill switch and process-match reclaim agent
- User-defined node taints with ownership tracking and drift reconciliation
- Kata containerd config delivery through an opt-in node agent
- `ScheduledCapacity` for schedule-gated, partial capacity on shared hosts
- Multi-instance controllers with consistent hashing, Prometheus metrics and health checks
- A hands-on workshop: https://github.com/firestoned/5-spot-workshop

# Challenges & Blockers

## Contributor concentration

Over 95% of non-bot PRs come from one maintainer. The other two listed maintainers are in the same organisation and have contributed little code this period. This is the project's main health risk.

## Adoption barriers

- 5-Spot targets a specific setup (CAPI plus bare-metal hosts that are shared with an incumbent workload). Trying it out needs more infrastructure than a typical Kubernetes operator, which slows outside evaluation. The `kind`-based e2e tier and the workshop are aimed at lowering that bar.
- The API is still pre-1.0 (`v1beta1` for `ScheduledMachine`, `v1alpha1` for `ScheduledCapacity`), and `v0.3.2` included a deliberate breaking change to `ScheduledCapacity`.

## Technical challenges

- Keeping pace with CAPI contract versions (`v1beta1` and `v1beta2`) and provider differences (kubeadm, k0smotron, CAPD).
- A high volume of dependency updates in a Rust and Kubernetes stack; currently handled with grouped Dependabot updates and auto-merge rules.

# Roadmap & Goals for Next 6 Months

## Goals

- Grow the contributor base beyond one primary maintainer, with at least one regular contributor from outside RBC.
- Move toward a stable API, ready for `v1`.
- Reach OpenSSF Best Practices "passing" and OSPS Baseline Level 2.

## Upcoming milestones

- Write `status.machineRef`, `bootstrapRef` and `infrastructureRef` on `ScheduledMachine` (currently declared but never written), decided through its own ADR.
- Run the `ScheduledCapacity` end-to-end suite against a built image and integrate with a consumer.
- Feature requests already filed: pin the controller to control-plane nodes to prevent deletion deadlock ([#61](https://github.com/finos/5-spot/issues/61)), and kill the Kubernetes node when the API becomes unreachable or on host events, so it never interferes with the incumbent workload ([#38](https://github.com/finos/5-spot/issues/38), [#39](https://github.com/finos/5-spot/issues/39)).

## Planned features/releases

- `v0.5.0`: `kube` 5.x upgrade, CRD schema fixes, status reference fields, node self-fencing.
- Continued work on the conversion-webhook shape for CRD multi-versioning (open decision in roadmap 01).

# TOC Support Needed

- **Cross-project collaboration**: introductions to FINOS members running bare-metal or hybrid Kubernetes who could evaluate 5-Spot, and to FINOS projects in the infrastructure and cloud space (for example, Common Cloud Controls and HTC-Grid) where scheduled capacity is relevant.
- **Contributor growth**: help promoting the project (FINOS blog, events, Open Source in Finance Forum) to bring in contributors from other organisations.
- **Lifecycle guidance**: clarity on what the TOC expects for OSPS Baseline Level 2 and what the path to Graduated looks like for a project with a concentrated contributor base.
